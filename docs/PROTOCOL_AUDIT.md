# Kawasaki EX500G: независимая проверка протокола

Дата: 2026-09-20. Это офлайн-аудит открытого кода; обмена с мотоциклом пользователя не было.

## Источники и степень подтверждения

1. [Zen3515/homeassistant-kawasaki-rideology-ble](https://github.com/Zen3515/homeassistant-kawasaki-rideology-ble), Apache-2.0, commit `06a0f61681e119f5e5dd9a793d8a61c891a020f8`. Автор подтвердил Z500 ER500F. Для EX500G совместимость декодирования ещё не проверена.
2. [agstrc/wazeology](https://github.com/agstrc/wazeology), Apache-2.0, commit `a8726cf562541738592b555bb0dbe4569f7003f4`. Отдельная реализация обмена с Kawasaki BLE5; Android-патч Waze для TFT, испытанный на Z900 SE «R Edition», Бразилия, MY2026. Это не приложение iOS и не доказательство навигации на LCD Ninja 500.
3. Пользовательские скриншоты: имена и UUID совпадают с обоими проектами; это подтверждает семейство GATT, но не набор поддерживаемой телеметрии.

| Назначение | UUID |
|---|---|
| Рекламируемый сервис нашего EX500G | `99EB13AC-42C9-4745-8B76-C30141401CE5` |
| Рабочий GATT-сервис | `92FAEC07-C075-4B7C-A6C2-BBD1D1A150F5` |

Рекламируемый UUID и рабочий UUID различаются: это важно для фонового поиска iOS. FEF5 в диагностическом приложении не используем.

## Минимальная диагностическая сессия

1. Connect, discover services/characteristics, назначить delegate/callback.
2. Подписаться на все три Notify и дождаться успешного подтверждения каждой подписки.
3. Через очередь отправить `03 00 00`, затем `40 00 00`. Ждать не только ATT write callback, но и соответствующего ответа; ACK отдельно сохранять. Таймаут конечный, повторы ограниченные.
4. При полученном валидном 0x40 можно запросить `41 00 00` (snapshot) и `45 00 00` (extended metrics). 0x45 в upstream ожидает ACK; поступление последующей телеметрии отдельно наблюдается.
5. Сохранять каждый входящий пакет с временем, UUID источника, исходными байтами. Нельзя считать BLE Connected доказательством работающей телеметрии.

Нет доказательства, что урезанная последовательность автоматически включает весь периодический поток 0x4A/0x4B. Поэтому первая версия должна честно показывать «протокол отвечает» и «телеметрия ещё не получена» отдельно.

## Кадры

Короткая команда: `[opcode, 00, argument]`. Последний байт обычно 00; у 0x42 он 01. Это не исходящий счётчик последовательности. В обоих проектах нет добавления checksum.

В 49 публичных fixtures входящий/примерный кадр имеет `[opcode, payloadLength, sequence, ...]`, `totalLength = payloadLength + 3`. Это проверено для fixtures, а не доказано универсально: wazeology строит исходящую навигацию 0x14 длиной 35 с byte1=08. Не переносить слепо правило на все команды.

Полученный BLE notify upstream обрабатывает как один законченный кадр; склейки/сборки фрагментов в обеих реализациях нет. Усечённые и неизвестные пакеты сохранять как raw и отмечать, не угадывать содержимое.

ACK коротких запросов: `[20,02,sequence,echoedOpcode,result]`; result00 принят,01 отклонён/не поддержан. Не применять позицию result универсально к длинным ACK: upstream использует byte7 для длинных, а ACK phone-name содержит текст и его generic result выглядит как ошибка ASCII. Для диагностики достаточно строго распознавать короткие ACK и сохранять остальные без классификации.

## Capability 0x40

Минимум 35 байт, корректный frame ID и полная заявленная длина. Индексы ниже с нуля.

| Поле | Mode |
|---|---|
| ecu_battery12V | b7 & 3 |
| engine_water_temperature | (b8 >> 6) & 3 |
| inlet_air_temperature | (b8 >> 2) & 3 |
| wheel_speed | (b9 >> 2) & 3 |
| engine_speed | b9 & 3 |
| gear_position | (b10 >> 4) & 15 |
| throttle_position | (b10 >> 2) & 3 |

Mode0/1 используются поддержанными схемами; 2 не декодировать,3 обозначает неподдерживаемость; у gear nibble также возможно F. Mode выбирает формулу, а не только boolean.

Валидность по upstream: config_retry_required, если хотя бы для одной тройки `(5,6,14)`, `(15,16,24)`, `(25,26,34)` верно `(bA != FF или bB != FF) и (bC & 1) == 0`. Невалидный capability не разрешает декодирование. Отсутствующий capability = unknown; не копировать opportunistic decode upstream.

## Формулы известных схем

| Поле / кадр | Формула и gate |
|---|---|
| RPM / 4A | mode0: `((b11 & 127)<<8) | b12`; mode1: `((b11<<8)|b12) / 4` |
| km/h / 4A | mode0: `((b9<<8)|b10) * 0.01220703125`; mode1: `((b9 & 1)<<8)|b10` |
| Gear / 4A | `b13 & 15`; upstream не содержит enum, N=0 пока требует проверки на байке |
| Throttle / 4A | mode0: `b14 * 0.78125`; mode1: `b14 * 100/255` |
| ECU battery / 41 | только mode0: `b14 * 20/256` вольт |
| Coolant / 45 | только mode1: `b17 - 40` °C; FF нет данных |
| Inlet air / 45 | только mode1: `b20 - 40` °C; FF нет данных |

Не превращать заполненные FF отсутствующие блоки в числа. При этом FF у throttle mode1 математически 100%; нельзя объявить каждый отдельный FF отсутствующим значением без знания поля. RPM/speed FFFF, gear nibbleF и temperatureFF не показывать как реальные измерения. Значения с неизвестной схемой, неподтверждённой валидностью или истёкшим временем свежести должны иметь статус unknown/stale и пустое текущее значение. Сохранять последнюю величину и timestamp отдельно; disconnect не превращает RPM в ноль.

В публичном Z500 0x40 поддержаны восемь полей: voltage, coolant, intake, injection, speed, RPM, gear, throttle. Odometer, fuel gauge, range и trip не поддержаны. Это не автоматически профиль EX500G.

## Что не включать в минимальный профиль

- 0x0B phone-name: записывает имя телефона, для запросов model/capabilities не нужен.
- 0x08 meter/log initialisation: известный профиль `[08,0C,00,FF,FF,0A,08,01,78,03,E8,00,C8,00,64]`; включение и параметры120/1000/200/100, полный смысл на EX500G не подтверждён. Может потребоваться для периодического потока, но не слать молча при первой пробе.
- 0x1B time sync / general settings,0x48 vehicle settings,0x1E service indicator: в upstream различаются запросные и изменяющие payload, убрать из первой диагностической сессии.
- 0x42 EMC и0x0A optional probe: не нужны для идентификации и неизвестный эффект в нашей комплектации.
- 0x13 meter indication keepalive и0x14 turn-by-turn из wazeology: это управление индикацией TFT; наш LCD не имеет подтверждённой поддержки.
- FEF5, firmware update, arbitrary raw-write UI: не требуется.

0x1A,0x1D,0x47 — дополнительные запросы capability; можно добавить позже при необходимости и наличии ответов. Управляющая характеристика Write необходима даже для запросов чтения, поэтому название «только запросы данных» точнее, чем обещание «ни одной записи Bluetooth».

## Полезное из wazeology

Очередь GATT: одна write operation за раз; уведомление-ответ может прийти до onWriteComplete — нужны два независимых флага. Конечные watchdog для connection/bond/subscribe/init, прогресс init продлевает таймаут, а общий процесс не висит. После CCCD готовности — init; сообщения об unsupported capability не приравнивать к готовности фичи. Android MTU request300/минимум48 нельзя копировать как API iOS: CoreBluetooth регулирует MTU сам.

## Проверка

`python3 -m unittest discover -s tests -v` в upstream: **9/9 PASS**.

`fixture_audit.py`: 49/49 fixtures проходят проверку declared length; команды совпадают; Z500 capability даёт 8 поддержанных /28 неподдержанных полей. Примеры: snapshot 41 =12.34375V;45 =40°C coolant и36°C intake.

Upstream tests не содержат реального кадра0x4A. Синтетический0x4A проверен на RPM3500,42km/h,gear3,throttle50.196%; это только проверка арифметики, не подтверждение результата на мотоцикле.

Java-тесты wazeology не запускались: в текущем окружении не найден javac. Их исходники прочитаны; нельзя писать, что они прошли.

Файлы: `audit.json` содержит результаты и fixtures без пользовательских данных. Этот каталог — рабочий офлайн-аудит, не установленное приложение.
